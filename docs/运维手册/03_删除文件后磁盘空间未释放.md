# 文件已经删除但磁盘空间没有释放：打开文件句柄排查

手册编号：OPS-003  
适用范围：Linux 上删除日志或临时文件后，文件系统空间仍被进程引用占用的情况。  
检索关键词：删了日志磁盘还是满、df 与 du 不一致、deleted、幽灵文件、open unlinked file、lsof +L1、日志轮转后空间不释放。

## 为什么删除路径后空间仍可能被占用

删除文件名会减少目录项与硬链接引用，但不会自动关闭进程已经持有的文件描述符。对于没有其他硬链接的文件，如果仍有打开引用，文件内容可以继续存在，直到相应引用释放。

因此，大日志已经从目录中消失，`du` 无法再沿原路径统计它，而 `df` 仍然显示空间被占用。进程甚至可能继续向这个已删除文件写入，使空间占用继续上升。

该现象不适用于所有 `df`/`du` 差异。快照、文件系统保留空间、权限导致的漏统计和挂载覆盖也能造成差异，应先确认目标挂载点。

## 第一步：确认磁盘与删除文件有关

```bash
findmnt -T /var/log -o TARGET,SOURCE,FSTYPE,OPTIONS
df -hT /var/log
sudo du -xsh /var/log
sudo lsof -nP +L1
```

前三条检查故障目录所属文件系统和可见目录占用，最后一条查找已打开但链接数小于 1 的文件。`/var/log` 是示例目录，实际应使用发生空间告警的路径。

`lsof` 输出中关注 COMMAND、PID、FD、TYPE、DEVICE、SIZE/OFF、NODE 和 NAME。NAME 可能带 `(deleted)`，FD 可能显示 `5w`、`7u` 等；用于 `/proc/PID/fd/` 路径时只使用其中的数字。

无权限看到某个进程不代表它没有持有文件。进程退出或句柄快速变化也可能使后续读取失效，需要重新采集，不要拿旧 PID/FD 直接执行处置。

## 第二步：确认占用的文件身份与实际块数

以下 PID 1234、FD 5 仅为示例，必须替换为刚刚确认的目标：

```bash
ps -p 1234 -o pid,ppid,lstart,comm,args
sudo readlink /proc/1234/fd/5
sudo stat -Lc 'device=%d inode=%i size=%s blocks=%b block_unit=%B' /proc/1234/fd/5
sudo cat /proc/1234/fdinfo/5
```

`ps` 用于确认进程身份和启动时间，降低把重用 PID 当作旧进程的风险。`readlink` 确认该描述符仍指向目标。`stat` 的 `size` 是逻辑长度，`blocks × block_unit` 表示分配块占用的一个估计；稀疏文件的逻辑大小可能远大于实际分配量。

以设备号和 inode 识别同一文件。一个文件被多个进程或多个 FD 打开时，不能把每个 FD 对应的大小重复累计。文件系统快照、共享块等也会影响最终释放量，因此块数估计不应承诺为精确可回收空间。

`fdinfo` 可以辅助查看偏移、打开标志和挂载标识。读写模式应结合 lsof 或打开标志解释；“打开文件”不等于“正在写文件”，日志处置不能只按文件名猜测。

## 第三步：找到拥有者与日志轮转方式

确认文件持有者属于哪个服务，以及服务是否支持重新打开日志。查看对应 systemd unit、服务文档和实际日志轮转配置。

```bash
systemctl status example-api.service --no-pager -l
systemctl cat example-api.service
sudo logrotate -d /etc/logrotate.conf
```

`example-api.service` 是示例。`logrotate -d` 只进行调试分析，不执行轮转；可以帮助检查配置是否包含正确路径和服务专用的重开动作。它不能证明上次轮转已成功，应结合服务日志和文件句柄变化。

轮转通常涉及重命名、创建新文件及通知写入者重新打开。服务继续持有旧文件时，只创建同名新文件不会改变旧 FD 指向。配置中的 postrotate 信号必须符合该服务文档，不能把某个服务的 USR1/HUP 用法套到所有进程上。

## 处理顺序与回退

优先使用服务官方支持的日志 reopen/轮转机制，使进程关闭旧日志并打开当前文件。执行前确认目标进程、文件和预期信号，执行后重新检查 FD；日志是否继续写入也必须验证。

如果服务没有可用的重开机制，且空间确实由其持有的文件占用，可在业务允许的维护或故障恢复流程中受控重启该服务。涉及多个持有者时，需要所有相关引用释放，单独重启一个进程可能不足以释放空间。

不要无条件对 `/proc/PID/fd/N` 执行 truncate。目标可能不是普通日志，可能包含业务数据；已删除文件的原路径也不能用于可靠定位。即使确认为普通日志，截断会丢失内容，进程后续写入方式还可能产生新的稀疏区域。

后续修复轮转配置时保留原配置版本；新配置验证失败则恢复配置。文件内容一旦删除或截断通常无法靠回滚配置恢复，所以正式处置前先保存确需保留的故障证据。

## 恢复验证与关闭条件

```bash
sudo lsof -nP +L1
df -hT /var/log
```

确认目标设备/inode 已不再由相关进程持有，文件系统可用空间有实际回升，新日志路径持续写入，业务请求保持正常。如果空间没有回升，应检查其他持有者及快照等原因，而不是重复删除路径。

结论应记录持有进程、设备与 inode、估算块占用、执行的重开或重启动作，以及 `df` 实际变化。若仅看到 `(deleted)` 但文件很小，不能把它当作磁盘满的主要原因。
