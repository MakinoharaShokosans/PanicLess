# Nginx 返回 502、504 与上游服务不可用排查

手册编号：OPS-001  
适用范围：Linux 上以 Nginx 作为 HTTP/HTTPS 反向代理的服务。容器环境需在实际处理请求的网络命名空间执行对应检查。  
检索关键词：网站打不开、接口超时、502 Bad Gateway、504 Gateway Timeout、Connection refused、upstream timed out、no live upstreams、upstream prematurely closed connection。

## 症状与排查入口

Nginx 返回 502 通常表示与上游连接、握手或响应处理失败；504 通常表示等待上游超时。状态码只能确定排查方向，不能单独证明“后端进程挂了”。网关前面如果还有负载均衡或 CDN，先确认错误由哪一层产生。

开始排查时记录请求域名、路径、时间、状态码及请求 ID。优先寻找同一请求在 Nginx access log、error log 和应用日志中的记录，避免把几分钟前的异常当作当前请求的原因。

本文中的 `api.example.com`、8080 端口、`example-api.service` 和 `/health` 均为示例，使用时替换为部署中的真实对象。不要假定本项目已经部署这些组件。

## 第一步：区分入口问题与上游问题

从用户所在网络或独立诊断机请求实际入口，观察状态码及阶段耗时：

```bash
curl --max-time 10 -sS -o /dev/null \
  -w 'code=%{http_code} connect=%{time_connect} first_byte=%{time_starttransfer} total=%{time_total}\n' \
  https://api.example.com/health
```

连接尚未建立就超时，应先检查 DNS、路由、防火墙或监听地址。已经收到 502/504，则继续定位返回错误的网关和上游。健康接口成功也不能证明其他业务路径正常，还需回看原失败路径。

在 Nginx 所在主机检查入口监听：

```bash
sudo ss -ltnp '( sport = :80 or sport = :443 )'
systemctl status nginx --no-pager -l
```

端口存在不等于请求命中了正确站点，需核对域名、监听地址、server_name 和 location。TCP LISTEN 的 Recv-Q 是等待应用接受的连接数量，瞬时非零不直接等于拥塞；持续接近队列上限才值得结合连接溢出和 accept 情况继续查。

## 第二步：找到实际请求对应的上游

检查启动方式与磁盘配置展开结果：

```bash
systemctl cat nginx
sudo nginx -T
```

`nginx -T` 展开配置与 include，可用于定位请求匹配的站点和 `proxy_pass`、`upstream`；它读取的是当前磁盘配置，不能证明运行中的 worker 已加载最新版本。部署修改过配置但尚未 reload 时，两者可能不同。配置输出可能包含内部地址和鉴权信息，排障记录只保留相关片段。

上游可能是 TCP 地址、Unix socket、多个 upstream 成员，或由变量和 DNS 解析得到。不能仅凭找到第一条 `proxy_pass` 就认定是当前请求的上游。

对于示例上游 `http://127.0.0.1:8080`，在 Nginx 执行环境中检查：

```bash
sudo ss -ltnp 'sport = :8080'
curl --max-time 5 -sS -o /dev/null -w 'code=%{http_code} total=%{time_total}\n' \
  -H 'Host: api.example.com' http://127.0.0.1:8080/health
systemctl status example-api.service --no-pager -l
```

直接请求应使用部署要求的协议、Host 和路径。若上游是 HTTPS，应单独检查 SNI、证书与信任链；若是 Unix socket，应检查 socket 路径、拥有者和 Nginx worker 的访问权限。

## 第三步：用错误日志决定下一跳

先从配置确定真实日志位置，再读取故障时间附近的内容：

```bash
sudo tail -n 100 /var/log/nginx/error.log
journalctl -u example-api.service --since '30 minutes ago' --no-pager -n 100
```

下面是典型日志特征示例，不是本项目的实际运行记录：

| 日志特征 | 优先判断与后续证据 |
| --- | --- |
| `connect() failed (111: Connection refused) while connecting to upstream` | 检查目标端口是否监听、地址是否正确、是否访问了错误容器或网络命名空间；也可能有主动拒绝连接的网络规则 |
| `upstream timed out ... while connecting to upstream` | 排查连接建立阶段：网络可达性、监听队列、上游接入能力 |
| `upstream timed out ... while reading response header from upstream` | TCP 已建立，继续查应用请求处理、数据库依赖、线程池和资源等待 |
| `upstream prematurely closed connection` | 上游提前断开；关联服务退出、应用异常或协议不匹配，不能直接认定 OOM |
| `no live upstreams` | 查看 upstream 成员和失败状态，确认是否所有成员被暂时判为不可用 |
| `Permission denied` | 检查文件/socket 权限及 SELinux/AppArmor 记录，不直接关闭安全机制 |

## 处理与回退

如果证据表明上游未启动，先按服务启动失败手册修复启动原因；不要仅重启 Nginx。若只有一个实例异常，可按现有变更流程摘除该实例，恢复时再加入，而不是同时重启整个服务组。

如果确认 Nginx 上游地址或协议配置错误，保存原配置后修改，先执行 `sudo nginx -t`。校验通过后才执行 `sudo systemctl reload nginx`，失败则恢复原配置并重新校验。reload 的影响与执行时间应记入排障记录。

连接已经建立但应用响应慢时，应修复阻塞依赖或容量问题。只有业务允许更长响应时间、上游耗时可预期时才调整超时；单纯提高 `proxy_read_timeout` 不能修复连接池耗尽或应用死锁。

## 恢复验证与关闭条件

恢复后同时验证原失败路径和健康接口，确认状态码及响应时间符合该服务正常基线。检查对应 error log 不再持续新增同类 upstream 错误，并观察多个请求或正常流量窗口，而不是只看到一次 200 就结束。

报告应包含：失败请求时间、命中的站点和上游、直接请求结果、关键日志、处理动作、恢复验证。DNS/TLS 问题分别参考 OPS-008、OPS-009；数据库连接等待参考 OPS-010。
