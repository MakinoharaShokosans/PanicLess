# 文件句柄耗尽与 TCP 连接状态排查

手册 ID：OPS-006  
适用范围：Linux 进程、systemd 托管服务、TCP 客户端与服务端。  
关键词：Too many open files、EMFILE、ENFILE、ulimit、LimitNOFILE、文件描述符、CLOSE_WAIT、TIME_WAIT、Cannot assign requested address、连接泄漏。

本文 PID `1234` 和 `example-api.service` 均为示例，操作前替换为实际目标。文中命令是只读诊断示例，已核对语法与工具手册，未在目标业务环境执行；读取其他用户进程或 socket 归属可能需要权限。

## 症状与首先要区分的错误

文件描述符不仅用于普通文件，也用于 socket、管道、eventfd 等对象。应用可能表现为无法打开日志、建立数据库连接或接受新的客户端连接。排查应先保存应用的完整错误及时间，不要只看到“连接失败”就提高所有限制。

| 报错 | 首先检查 |
| --- | --- |
| `Too many open files` / EMFILE | 目标进程的已打开描述符与软限制 |
| `Too many open files in system` / ENFILE | 系统文件表使用情况，结合具体内核报错 |
| `Cannot assign requested address` / EADDRNOTAVAIL | 绑定的本地地址是否存在，或出站临时端口是否紧张 |
| `Connection refused` | 目标监听、地址和网络策略，不先归因于 fd 上限 |

## 第一步：检查目标进程的实际限制

```bash
ops_pid=1234
ops_service='example-api.service'
cat "/proc/$ops_pid/limits"
systemctl show "$ops_service" -p MainPID -p LimitNOFILE -p LimitNOFILESoft
cat /proc/sys/fs/file-nr
cat /proc/sys/fs/file-max
```

`/proc/<pid>/limits` 的 Max open files 给出目标进程的软、硬限制，软限制是当前常见的约束。登录终端里的 `ulimit -n` 只反映该 shell 及其后代，不代表已经由 systemd 启动的服务。

systemd 配置值和目标进程实际值应互相核对，应用可能在启动后自行调整限制。`file-nr` 是系统范围的文件句柄统计，不等于某个进程的 fd 数量，也不能把所有进程的 fd 简单相加后直接与 file-max 等同。以完整错误类型决定查进程限制还是系统资源。

## 第二步：计数并判断描述符种类

```bash
find "/proc/$ops_pid/fd" -mindepth 1 -maxdepth 1 -type l -printf '.' | wc -c
ls -l "/proc/$ops_pid/fd"
```

计数命令为每个 fd 链接输出一个字符，最终得到一次近似快照。进程在采集期间可能打开或关闭 fd，因此接近上限时应短间隔重复观察，并记录 PID 的启动时间，避免进程重启后误接续旧样本。先确认目录可访问；出现 Permission denied 或进程消失时，不能把输出零当作零使用量。

链接目标为 `socket:[inode]` 表示 socket，`pipe:[inode]` 表示管道，`anon_inode:` 表示内核匿名对象。普通路径可以揭示重复打开的日志或配置文件。找到数量最多的类型后继续关联，不能仅凭“socket 多”就认定连接泄漏。

若安装了 lsof，可以补充查看：

```bash
lsof -nP -p "$ops_pid"
```

lsof 输出还包括 cwd、rtd、txt、mem 等记录，不能直接把其全部行数当作打开 fd 数量。大规模进程可能产生较多输出，应限定单个已确认的 PID。

## 第三步：区分 CLOSE_WAIT 与 TIME_WAIT

```bash
ss -tanp state close-wait
ss -tan state time-wait
ss -s
cat /proc/sys/net/ipv4/ip_local_port_range
```

`ss` 默认观察当前网络命名空间；容器里的连接不一定出现在宿主机当前视图。`-p` 的进程信息受权限影响，缺少 PID 不代表 socket 无归属。应把 socket 的本地/远端地址、端口和进程信息关联到目标 PID。

CLOSE_WAIT 表示 TCP 已收到对端关闭通知，本地应用仍未完成关闭。短暂出现是正常阶段；如果同一进程的 CLOSE_WAIT 持续积累、fd 数量同步上升，并在请求结束后不回落，才支持应用释放连接不及时的判断。

TIME_WAIT 通常发生在应用关闭 socket 之后，由内核保留连接状态，通常不再占原进程的打开 fd。大量 TIME_WAIT 应关注短连接频率、连接复用及特定目的端的临时端口可用性，不能把 TIME_WAIT 数量直接算进目标进程 fd 使用量。`ss -s` 是当前命名空间汇总，不是某个应用的连接计数。

## 处理分支与变更条件

如果打开 fd 已接近软限制且数量与合理并发一致，可在容量评估后调整该服务的 LimitNOFILE；保存旧配置，按服务支持方式重新启动使限制作用于新进程，再读取 `/proc/<新PID>/limits` 确认。仅在终端执行 ulimit 不会改变已运行服务。提高限制前还应确认应用使用的 I/O 机制支持目标规模。

如果 fd 在稳定负载下持续增长，应修复应用关闭文件、socket、响应体或异常路径的逻辑，并检查连接池回收设置。提高上限只能延迟复发；短期恢复需配合减少并发或受控重启，保留恢复前统计供定位。

如果是出站地址不可用，先检查绑定 IP 是否存在，再检查连接复用与临时端口压力。不要把随意缩短 TCP 超时或修改全局内核参数作为默认操作。配置修改应有原值记录，验证无改善时恢复原值。

## 恢复验证与易混淆情况

恢复标准：新的连接和文件操作成功；目标进程 fd 数量在代表性负载下保持稳定且有余量；CLOSE_WAIT 在连接结束后能够下降；应用不再出现对应 EMFILE、ENFILE 或 EADDRNOTAVAIL。恢复验证应覆盖一次完整请求生命周期，而不只检查服务处于 active。

文件打开但已删除的问题属于磁盘空间释放链，与“fd 数达到上限”可能同时存在但不是同一件事。进程 fd 使用率、系统文件表、连接状态和临时端口必须分别记录，避免用一个计数解释所有网络故障。
